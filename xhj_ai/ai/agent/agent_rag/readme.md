## RAG
公司内部的Agent 基本都要用到RAG。
llm能思考，但不知道公司内部的文档，我们需要基于内部文档来回答。
这个流程太固定了，有些缺点
- 所有问题都走RAG检索？简单问题不需要检索，浪费资源（token和检索，增强流程）
  两个分支 ，简单问题大模型直接回答，复杂问题走RAG检索。
  调用llm 来判断是否是简单
- 没有纠错和评估机制，无法判断检索内容是否精确，是否足够。
  llm 评估函数
- 处理不了需要多部步检索的复杂问题，比如先查A，再查B 才能得出结论。
  天龙八部中四大恶人排行第二的是谁？此人之子在身世揭晓前其生父在武林中的公开身份是什么？
  llm 规划能力 拆分 分步骤
- 专业术语、精确实体更适合关键词检索，纯语义检索容易匹配不准。
  mysql like 检索 正则 文字匹配
  如高血糖、低血糖  从自然语义相似度来讲是很接近的
  需要关键词检索
- 本地知识库没有的内容
  llm 胡说
  去网络搜索补充

死板的检索生成 流程，升级为可思考可判断、可纠错的智能RAG架构。
