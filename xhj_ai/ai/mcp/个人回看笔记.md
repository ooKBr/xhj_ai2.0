### 4.2 逐词解析表格
| # | readme 里的词 | 技术对应物 | 干的事 |
|---|---|---|---|
| 1 | `cc prompt` | 你在 Claude Code 输入框里敲的内容 | 触发整个链路的起点 |
| 2 | `llm` | Host 调的模型（Claude Sonnet / 通义等）| 第一次推理：这个问题直接答还是用工具？ |
| 3 | `分析` | LLM tool calling 的推理步骤 | 工具选择 + 参数填充 |
| 4 | `选中fs client` | Host 根据 `mcp.json` 定位到 simple-read-mcp 那个 server 条目 | 找到对应的子进程启动配置 |
| 5 | `stdioServerTransport` | Host（Client 侧）传输类 | 把 JSON-RPC 序列化成一行 JSON，写进子进程 stdin |
| 6 | `stdin` | 父子进程共享的"进水管"（Standard Input，OS 级管道）| Host 写请求的通道 |
| 7 | `server` | `simple-read-mcp/server.js` 的 McpServer 实例 | 找到对应 handler → 调 `fs.readFile` |
| 8 | `执行返回` | handler 拼好 `{ content: [{type:'text', text: fileContent}] }` | 按 MCP 规范返回 |
| 9 | `stdout` | 父子进程共享的"出水管"（Standard Output）| Server 写响应的通道 |
| 10 | `StdioServerTransport` | Server 侧传输类 | 把响应序列化一行 JSON，写进 stdout |
| 11 | `cc` | 回到 Claude Code Host 侧 | Client 按 id 匹配对应请求，把 content 存起来 |
| 12 | `llm -> generate` | Host 把 content 拼进 prompt 再发一次 LLM | 第二次推理：基于内容生成最终回答给你 |

> 🔑 关键要点：**LLM 被调用了两次**。第一次"选工具+填参数"，第二次"基于工具返回的真实内容生成答案"。这就是 RAG 的 R+A+G 三步。

## 五、新旧写法速查卡（以后加新工具直接套）

### 5.1 新版（推荐）：McpServer + zod
```js
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { StdioServerTransport } from '@modelcontextprotocol/sdk/server/stdio.js';
import { z } from 'zod';

const server = new McpServer({ name: 'xxx-mcp', version: '1.0.0' });

// 新工具直接复制这块模板（复制 20 行 / 改 3 处：工具名 / 描述 / schema / handler 里的真逻辑）
server.tool(
  "tool_name",
  "工具一句话描述，AI 推理时用",
  { arg1: z.string().describe("参数描述"), arg2: z.number().min(0).describe("正数") },
  async ({ arg1, arg2 }) => {
    try {
      const r = await doRealWork(arg1, arg2);
      return { content: [{ type: 'text', text: String(r) }] };
    } catch (e) {
      return { isError: true, content: [{ type: 'text', text: `失败：${e.message}` }] };
    }
  }
);

async function main() {
  const transport = new StdioServerTransport();
  await server.connect(transport);
  console.error("[xxx-mcp] started (stdio)");  // ✅ stderr
}
main().catch(console.error);
```

### 5.2 旧版：Server + setRequestHandler + 手写 JSON Schema（对照用）
```js
import { Server } from '@modelcontextprotocol/sdk/server/index.js';
import { StdioServerTransport } from '@modelcontextprotocol/sdk/server/stdio.js';
import { ListToolsRequestSchema, CallToolRequestSchema } from '@modelcontextprotocol/sdk/types.js';

// ⚠️ 必须手写 capabilities，拼错直接废
const server = new Server(
  { name: 'xxx-mcp', version: '1.0.0' },
  { capabilities: { tools: {} } }
);

// ① tools/list 注册（每加一个工具要在 tools 数组里再加一条对象）
server.setRequestHandler(ListToolsRequestSchema, async () => ({
  tools: [{
    name: 'tool_name',
    description: '...',
    inputSchema: {
      type: 'object',
      properties: {
        arg1: { type: 'string', description: '参数描述' },
        arg2: { type: 'number', minimum: 0, description: '正数' }
      },
      required: ['arg1'],  // ⚠️ 和 properties 平级！缩进错 = 白写
    }
  }]
}));

// ② tools/call 注册（每加一个工具要在 switch 里再加 case）
server.setRequestHandler(CallToolRequestSchema, async (req) => {
  const { name, arguments: args } = req.params;
  if (name === 'tool_name') {
    try {
      const r = await doRealWork(args.arg1, args.arg2);
      return { content: [{ type: 'text', text: String(r) }] };
    } catch (e) {
      return { isError: true, content: [{ type: 'text', text: `失败：${e.message}` }] };
    }
  }
  throw new Error(`未知工具：${name}`);
});
```

### 5.3 对比结论
```
代码量：      新版 20 行 / 每工具  →  旧版 60+ 行 / 每工具
拼写坑：      新版无（McpServer 自动推 capabilities）→  旧版 capabilities/tool 容易拼错
```

## 六、踩坑清单（8 条真实炸过的，每条一句话修复）
| # | 症状 | 根因 | 修复一句话 |
|---|---|---|---|
| 1 | `ERR_MODULE_NOT_FOUND: Cannot find module .../server/stdio imported from...` | import SDK 内部路径**没带 `.js` 后缀**，exports map 严格匹配不补扩展名 | `server/stdio` → `server/stdio.js`，所有内部子路径一律补 `.js` |
| 2 | `ERR_MODULE_NOT_FOUND: .../server/schema.js` | `server/schema.js` SDK 里**根本不存在**这个文件，想当然猜路径 | Schema 统一写 `import { ListToolsRequestSchema, CallToolRequestSchema } from '@modelcontextprotocol/sdk/types.js'` |
| 3 | `Server does not support tools`（旧版） | `capabilities` 拼错成 `capabolities` 或 `tools` 少 s 写成 `tool` | 用新版 McpServer，不用自己写 capabilities，彻底避免 |
| 4 | Agent 传了空 path 也进来了，然后 `fs.readFile` 炸 | 旧版 JSON Schema `required:['path']` **缩进错写到 properties 内部**，等于没声明 | 用新版 zod，`z.string()` 默认必填、位置必对 |
| 5 | Host 连 server 握手失败、解析 JSON-RPC 报错 | 启动日志用了 `console.log('服务已启动')` —— 写进了 stdout 协议通道，Host 当成一条 JSON-RPC 去 parse 就炸 | 调试 / 启动日志一律 `console.error` 打 stderr，或重定向到文件 |
| 6 | `ERR_MODULE_NOT_FOUND: .../posts-embedding.json`（顺便记一下 RAG 那边的） | 相对路径 `./data/xxx.json` 是相对于 cwd 不是脚本目录，换目录跑就炸 | ESM 里用 `import.meta.url` + `fileURLToPath` + `path.dirname(__dirname)` 拼绝对路径 |
| 7 | `SyntaxError: Unexpected token '.'` | 链式调用中间写了分号，链被截断 | 一条 `.a().b().c()` 中间不能有分号，分号只能写在链的最后一行 |
| 8 | CC 里报 `No MCP servers configured` | 你把 `.mcp.json` 放在项目子目录（`mcp-test/.mcp.json`），Claude Code 根本不去那里找 | 全局配置放在 `C:\Users\xhj\.claude\mcp.json`（Windows）；写完要重启 CC 才生效 |

## 八、资源 vs 工具对照卡（对应 `mcp/readme.md#L36-41`）
MCP 协议里 resource 和 tool 是两个**不同能力**，但初学者容易混。一张对照表讲清：

| 维度 | Resource（资源）| Tool（工具）|
|---|---|---|
| 例子 | 文件内容、DB 某一行、飞书文档原文 | 读文件（这里 read_file 虽然像 resource，但我们用 `.tool()` 注册的所以算 tool）、发邮件、执行命令、创建日历 |
| 本质 | **数据**（被看到的东西） | **动作**（会产生副作用的东西） |
| SDK 注册方式 | `server.resource(name, uriTemplate, desc, handler)` | `server.tool(name, desc, zodSchema, handler)` |
| 列出方法 | `resources/list` | `tools/list` |
| 调用方法 | `resources/read` | `tools/call` |
| 缓存 / 订阅 | ✅ 可以订阅变更通知（比如文件变了自动推）| ❌ 一般不缓存，每次直接执行 |
| simple-read-mcp 里怎么选？ | 如果只是"读文件内容给模型看"，用 resource 更准确；但如果以后想加"写文件 / 删文件"，统一用 tool 更顺手 | 我们目前用 `.tool()` 注册了 read_file，实际效果一样能拿到内容 |

> 💡 简单判断口诀：**"如果这个操作会产生副作用（改/删/发/执行）→ 一定是 tool；如果只是让模型看到点东西 → resource 更准确，但为了后续扩展方便也可以统一注册成 tool。"** 我们这个 simple-read-mcp 就是后者（为了以后加 write_file 直接加第二个 server.tool 就行）。
